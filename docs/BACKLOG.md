# Release Radar — порядок работы (по таймлайну)

Не по слоям/логике, а в том порядке, как реально собирать. Шаги 1→10 идут друг
за другом. В каждом шаге — конкретные чекбоксы, отмечай сверху вниз. Где порядок
не жёсткий, стоит ⚠️ и от чего он зависит. Детали эффектов/схем — в
[`IMPLEMENTATION.md`](./IMPLEMENTATION.md).

Легенда: [x] готово · [ ] сделать · ⚠️ может зависеть от …

## Уже готово (не трогаем)

- [x] базовый проект, `pnpm check / lint / test / build` зелёные
- [x] добавить npm-пакет и увидеть его в списке
- [x] кнопка `Check now` (pending-state + показ ошибки)

## Шаг 1. Сделать так, чтобы `Check now` что-то показывал

Сейчас проверка тянет данные из npm и выбрасывает их. Сделай видимый результат.

- [ ] 1.1 `release.ts`: тип `Release` — version, publishedAt, url (Schema +
      тест)
- [ ] 1.2 в `check-monitor.ts` перестать терять результат: взять latest
      version + publishedAt, построить `Release`
- [ ] 1.3 хранить `lastRelease` у монитора (пока in-memory)
- [ ] 1.4 прогнать релиз через `evaluateReleaseGate` → статус + `eligibleAt`
- [ ] 1.5 показать в `MonitorListItem`: версию, `publishedAt`, статус
      (`cooling_down`/`ready`/`date_unknown`), дату `eligibleAt`
- [ ] 1.6 сообщения i18n для статусов

Готово, когда: жмёшь `Check now` — видишь версию, дату публикации и «готна ли
она». Оценка: ~1–2 ч.

⚠️ «Пока in-memory» — если хочешь, чтобы данные выживали перезапуск раньше,
перенос SQLite (Шаг 3) вставь сразу после этого шага.
